# v1.2 进度系统设计

更新日期：2026-06-03

本文件只记录 v1.2 进度系统设计，不直接承担开工拆任务。v1.1 已发布后，启动前审查和第一批 PR 切法记录在 `docs/handoff-v1.2.md`。

当前状态：v1.2 已进入数据基础阶段。启动期 category 矩阵口径已裁决为当前 8 个有内容类别；后续仍需确认 localStorage 版本策略和 ruff WASM 降级标准。

## 一句话定位

进度系统不是 leetcode 式刷题进度，而是“认知外脑”的掌握度地图。形态必须服从这个定位：它要展示学习者的知识形状、证据来源和下一步空缺，而不是把学习压成一个百分比。

## 核心改进

### 一维进度条改为二维矩阵

知识图谱是网状结构，单根进度条会把偏科形状压成一个数字。v1.2 启动期使用 `8 类别 × 4 档` 的掌握度矩阵，让用户一眼看到：

- 哪些类别已经点亮。
- 哪些类别只会语法但还不会功能。
- 哪些类别缺少工程证据。
- 下一步最值得补哪一个 cell。

### 限时编程改为 5 种评估累积证据

限时编程只测一部分能力，容易把项目拉回刷题平台。v1.2 的评估证据由 5 种题型共同累积：

- 识别题：判断概念、代码行为、错误来源。
- 改错：定位 bug 并解释修复。
- 补全：补齐关键语句或函数。
- 限时编程：在时间限制内通过测试用例。
- 重构：把可运行代码改成更清晰、更工程化的版本。

## 四档判定

四档必须可机器验证，不能依赖主观自评。

| 档位 | 名称 | 机器可验证条件 |
|---|---|---|
| Tier 1 | 会语法 | 读过 15 个概念 + 通过 10 道识别题 + 跑通 8 段 `standard` 代码 |
| Tier 2 | 会功能 | 5 道限时题通过测试用例 + 3 道通过 PEP 8 检查 |
| Tier 3 | 会工程 | 完成 1 个 `stage: entry` 项目 + 1 段 `production` 代码 |
| Tier 4 | 融会贯通 | 完成 1 个 `mid` / `capstone` 项目 + 2 次反向识别 + 1 道跨概念题 |

矩阵 cell 状态由证据计算，不由用户手动标记。用户可以看到证据明细，但不能直接把自己标成高档。

## 实时反馈三层

v1.2 的反馈分三层，分别服务不同时间尺度：

- 键盘层（毫秒）：编辑器语法高亮、错误下划线。
- 运行层（秒）：Pyodide 跑测试，可视化哪些用例通过、哪些失败。
- 进度层（提交后）：显示例如 `+20% Tier 2 进度`，并立即点亮矩阵 cell。

Pyodide 只在用户点击“开始评估”后加载，不进入首屏。进度页本身必须继续保持轻量。

## 回看维度

进度系统不记录“学了多久”作为核心指标，而记录“认知发生了什么”：

- 本周完成了哪些具体证据。
- 最近卡壳的共同模式是什么。
- 当前图谱活跃前沿在哪里。
- 哪些类别长期停留在低档。

v1.2 只做轻量反向触发：

- 停留触发：用户长时间停在某个概念页时，弹出一题轻量识别题。
- 沉默提醒：长时间没有新增证据时，提醒用户回到最近的活跃前沿。

不做完整 SM-2，不做复杂复习日程。

## 数据模型

### 新增 assessments collection

题库纯静态进入 `src/content/assessments/`。建议 schema：

```typescript
kind: z.enum([
  "recognition",
  "debugging",
  "completion",
  "timed-coding",
  "refactor"
])
targetTier: z.enum(["tier1", "tier2", "tier3", "tier4"])
concepts: z.array(slugRef).min(1)
timeLimit: z.number().int().positive().optional()
testCases: z.array(z.object({
  name: z.string(),
  input: z.unknown().optional(),
  expected: z.unknown().optional(),
  code: z.string().optional()
})).default([])
referenceSolution: z.string().optional()
rubric: z.array(z.string().min(1)).min(1)
```

5 种评估各自都要有示例，不允许只做限时编程题。

### localStorage key

v1.2 继续纯本地，不接后端，不做用户系统或跨设备同步。

- `pkb:progress`：矩阵 cell、当前档位、证据摘要。
- `pkb:attempts`：每次评估提交记录，包含 assessment id、结果、耗时、测试结果和时间戳。
- `pkb:timetrack`：轻量时长记录，只用于回看辅助，不作为核心成就指标。

### progress calculator

新增纯函数模块：

```text
src/lib/progress-calculator.ts
```

职责：把 `attempts` 计算成掌握档位和矩阵 cell 状态。它必须是无 DOM、无 localStorage、无 Pyodide 的纯函数，方便单测覆盖。

输入输出方向：

```typescript
attempts -> {
  matrix,
  tiersByCategory,
  evidenceByCell,
  activeFrontier,
  recentPatterns
}
```

## 技术决策

这 4 条提前钉死，避免实施期反复摇摆：

- 编辑器用 CodeMirror 6，不用 Monaco。目标是控制前端体积，保护 Lighthouse。
- Pyodide 只在点击“开始评估”后加载，不在首屏加载。
- PEP 8 检查优先尝试 ruff WASM 在浏览器运行；阶段 A 先验证可行性，失败则降级为建议层，不阻断主流程。
- 纯 localStorage，不接后端，不做用户系统，不做跨设备同步。

## 不做清单

v1.2 明确不做：

- 积分
- 徽章
- 连击
- 排行榜
- 社交比较
- AI 自动出题
- 完整 SM-2
- 后端账号系统
- 跨设备同步

这些机制会把项目拉向刷题平台或运营系统，不符合“认知外脑”的定位。
